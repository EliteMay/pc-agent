# v0.12 Windows no-clobber move: implementation design and release gate

Status: **design only / not approved for deployment**. Tracks [Issue #27](https://github.com/EliteMay/pc-agent/issues/27) and draft [PR #26](https://github.com/EliteMay/pc-agent/pull/26).

## Problem and temporary safety policy

Node `fs.renameSync(source, destination)` is called after a separate
`existsSync(destination)` check. Another process can create the destination in
between; the implementation cannot promise "never overwrite". The production
`registerSafeWriteTools` therefore **does not register `move_path`** until a
proper provider and adversarial tests pass. Keep that fail-closed default in
place; do not add a configuration flag that simply turns the unsafe rename
path back on.

The legacy `move-path.js` implementation and its direct-call regression tests
remain for development, not remote execution.

## Proposed Windows implementation

Use a small trusted Windows-native operation boundary that ships with the
Manager, not a shell command assembled from queued strings.

1. Expose one fixed operation: `move_no_replace(source_path, destination_path,
   approved_source_identity, allowed_roots)`. Inputs are data, not code or
   command-line fragments. Authenticate the local caller and bound request size.
2. In native/.NET interop, open a handle to the **source** using Windows
   `CreateFileW` with the permissions and sharing modes required for renaming.
   For a directory, handle opening requires `FILE_FLAG_BACKUP_SEMANTICS`.
   Reject symbolic links/reparse points and unsupported file types according
   to the policy. Compare the *opened object* identity (e.g. volume and file
   ID via `GetFileInformationByHandleEx(FileIdInfo)`) with the approved object.
   A path-only `stat` before a rename is insufficient.
3. Open the **destination parent** as a trusted directory handle. Check its
   resolved final path and the source final path against canonical allowed
   root identities using the same Windows path-normalization rules. Explicitly
   reject path components that redirect outside allowed roots. Decide how
   relocation of an allowed-root directory while handles remain open is
   prevented or detected; merely resolving a name once is insufficient.
4. Rename the *source handle* with
   `SetFileInformationByHandle(FileRenameInfo, FILE_RENAME_INFO)`, with
   `ReplaceIfExists = FALSE`. Supply the target file name **relative to the
   opened destination directory handle** using `RootDirectory` when supported.
   Do **not** set `FILE_RENAME_REPLACE_IF_EXISTS`, POSIX replacement semantics,
   `MOVEFILE_COPY_ALLOWED`, or any other replacement/fallback behavior.
   An existing destination must cause the operation to fail atomically, even
   when another process created it milliseconds earlier.
5. Keep source and destination-parent handles alive through the rename
   boundary. Verify post-operation result and report a structured failure
   without deleting or replacing any third-party destination.
6. Limit the first provider to regular files if that is necessary. Directory
   moves must remain disabled until directory content/reparse-point and
   descendant-scope semantics are defined and tested. File-system permissions,
   hardlinks, and directory descendants require an explicit threat-model
   review.
7. On helper absence, helper version mismatch, failed identity check,
   unsupported filesystem, or uncertain outcome: **fail closed**. Do not
   retry a possibly completed mutation automatically; keep the journal's
   `UNKNOWN_OUTCOME` semantics.

## Acceptance tests (must run on Windows)

- Normal file rename within one allowed volume succeeds and preserves bytes.
- Already existing file or directory destination is not replaced.
- **Deterministic race:** insert a test barrier immediately before the
  handle-based rename, create a different destination, then release the
  barrier. Assert `move_no_replace` fails, competing destination bytes and
  identity are unchanged, and source remains.
- Source object replaced with same-size/same-content file after approval:
  fail without moving substitute.
- Source object replaced after validation but before native handle opening:
  fail without moving substitute.
- Destination parent replaced by a junction to a directory outside allowed
  roots: fail without writing outside.
- Source parent replaced by a junction outside allowed roots: fail.
- No cross-volume move/copy fallback, including junction/reparse mount points.
- Root-move, move-into-own-descendant, sensitive file/dir, reserved names,
  alternate data streams: fail.
- Process crash/timeout after native operation: journal reports uncertain
  outcome and does not blindly retry or perform unsafe cleanup.
- Different Windows filesystem types and file permissions: explicitly
  document supported matrix; unsupported cases fail closed.
- Agent CI, Manager CI, and an independent physical Windows PC all green
  on the **same final commit SHA**.

## Re-enable criteria

Only re-register `move_path` when all acceptance tests pass and review
confirms that the native helper's guarantees match the public tool description.
The test `unsafe move_path stays unavailable in the runtime registry` must
then be replaced with tests proving the safe provider is the only
registration path; do not silently weaken it.

## Windows API documentation

- [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info): `ReplaceIfExists = FALSE`
  returns an error if the target name exists; `RootDirectory` can hold the
  directory for a relative target name.
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle):
  mutate an opened file object using a handle with the required access rights.
- [MS-FSCC FileRenameInformationEx](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c):
  replacement is explicitly gated by `FILE_RENAME_REPLACE_IF_EXISTS`.

**Design limitation:** these docs describe available Windows API semantics.
They do not by themselves prove the specific interop code is race-safe.
That proof requires the adversarial Windows tests and review above.

## Approval identity and reparse-race research prototype (2026-10-08)

The Manager now has **test-only** `CaptureApprovalForTest` and a guarded
`MoveFileForTest(..., approved, operationId)` code path. No normal Agent or
Manager UI uses these methods.

The capture stores an immutable in-memory snapshot of:

- the approval operation ID and exact source/destination/allowed-root paths;
- Windows object IDs (volume serial + file indices) for source, destination
  parent, and allowed root, from `GetFileInformationByHandle`;
- source length and last-write metadata, plus normalized final paths observed
  via `GetFinalPathNameByHandleW`.

The test-only executor compares those values against opened handles and a
fresh lookup of each pathname, both **before** and **after** an injected
precommit test callback. It rejects mismatched operation IDs, swapped source
files with identical bytes, different destination-parent directory objects,
and moved parent handles. Capture and revalidation refuse source/destination
paths outside the canonical allowed root and reparse entries at directly
opened filesystem objects.

Windows regression scenarios added:

- unchanged approved file can be moved within the allowed root;
- approved source replaced by a new file with the same bytes: denied;
- destination parent replaced after approval: denied;
- destination parent replaced after handles were opened, at a deterministic
  precommit barrier: denied;
- source outside the allowed root: denied;
- **junction redirect** of the destination parent to an outside, disposable
  test fixture at the precommit barrier: denied, no file appears outside;
- approval for operation A cannot be reused as operation B.

### Security limits (release blockers still open)

1. **Not atomic with path resolution.** The native
   `SetFileInformationByHandle(FileRenameInfo)` call currently uses a full
   destination pathname because `RootDirectory` did not work in the tested
   Win32 code path. The destination parent can still change in the tiny
   interval between the final validation and this kernel operation. These
   deterministic tests narrow the observable window but **cannot prove that
   an arbitrary attacker cannot exploit it**.
2. **No end-to-end approval transport.** The snapshot is an in-memory
   .NET test object, not a signed remote payload nor a hooked-up Agent
   approval result. `operationId` binding demonstrates the intended contract
   but is not yet an authenticated cross-process protocol.
3. **Only regular files are eligible.** Directory moves, recursive sensitive
   child checks, mount/reparse complexities, SMB/network filesystems, and
   hardlink threat modeling are not complete.
4. **Parent/root relocation races remain.** The opened handles are kept
   alive, but the absolute destination path is still re-resolved by Windows.
   Implement and prove a handle-anchored, atomic no-replace operation before
   exposing the helper to any normal Agent caller.
5. **Deployment disabled.** `move_path` stays unregistered in
   `registerSafeWriteTools`. Do not weaken or bypass the negative registry
   test. See security release gate [Issue #27](https://github.com/EliteMay/pc-agent/issues/27).

The junction test uses `cmd /c mklink /J` **only to create a disposable test
fixture in Windows CI**, not as any application command execution feature.


## NT handle-relative rename research (2026-10-08)

An additional **test-only** implementation is now isolated in
`manager/PcAgentManager/Services/WindowsNtAnchoredMovePrototype.cs`. It is
called from `WindowsNoReplaceMovePrototype.MoveFileForTest` only when the
explicit `useNativeRelativeMoveForTest: true` argument is supplied together
with the local approval snapshot and matching operation ID. **The normal
Agent registry still does not expose `move_path`.**

### Mechanism and observed Windows CI results

- Uses the native `ntdll!NtSetInformationFile` interface with
  `FileRenameInformation` and a `FILE_RENAME_INFORMATION` buffer that sets
  `ReplaceIfExists = FALSE`, `RootDirectory` to an already-open destination
  parent **handle**, and `FileName` to one validated relative leaf.
- The Windows API is asked to do a single no-replace rename of the opened
  source handle relative to that directory object. It is not passed a mutable
  absolute destination pathname at this final operation.
- Native NTSTATUS failures are converted with `RtlNtStatusToDosError` and
  treated as failure. A pending/uncertain outcome is never automatically
  retried; no cleanup blindly removes a possible competing destination.
- In addition to approved object identity/final-path revalidation, source and
  destination parent directory chains from the allowed root are opened with
  sharing that excludes `FILE_SHARE_DELETE`, and are kept alive until the
  final native operation. This is intended to prevent intermediate parent
  relocation in ordinary Windows filesystem scenarios.
- Functional commit `3cdfbb1` passed **Agent CI and Manager CI**, including
  successful native move, preexisting destination, last-moment competing
  destination, direct parent relocation prevention, and equal-byte source
  replacement refusal. Follow-up directory-chain guard tests run separately.

### Important limitations and remaining release blockers

1. `NtSetInformationFile` is documented in the Windows driver/NT-native API
   documentation. Shipping it through user-mode `ntdll.dll` raises
   compatibility and support questions; working GitHub Actions tests do not
   establish support on all target Windows builds/filesystems.
2. The current chain lock begins at the configured root. An ancestor **above**
   that root could be renamed, and supported semantics for rename/mount-point
   races across ancestor objects still need analysis and adversarial tests.
3. The snapshot captures source file ID, size, and last-write metadata, but
   does not bind the full file content to a cryptographic hash nor lock all
   writers. Approval scope and source modifications through other handles or
   hardlinks need further threat-model review.
4. Destination names are checked for ordinary Windows-invalid patterns,
   but edge cases (8.3 aliases, case sensitivity, hardlinks, mount points,
   unusual filesystems, and network targets) require additional validation.
5. This is an **internal test-only experiment** with no authenticated
   cross-process helper protocol and no Agent integration. Do not use the
   regression tests as grounds to re-enable `move_path` or merge PR #26.

Reference: [Microsoft NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile)
for native `FileRenameInformation`; see [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)
for no-overwrite intent.


## Content integrity and volume-ancestor guard research (2026-10-08)

An additional **test-only** guard is implemented in the .NET move prototype:

- Capture SHA-256 of at most 64 MiB from the **opened source handle**, as part
  of its locally approved immutable snapshot. Recompute that digest through
  the opened handle before each native rename. This rejects modifications to
  the original file even if its length and last-write timestamp are restored.
- While the NT-relative move is executing, its source file is opened without
  `FILE_SHARE_WRITE` or `FILE_SHARE_DELETE`. Concurrent open-for-write
  requests ordinarily fail with a sharing error. Test-only callbacks exercise
  this behavior at the last precommit boundary. This is **not** a claim that
  memory-mapped writes, filesystem-specific behavior, or all hardlink races
  have been eliminated.
- Extend open-handle no-delete guards from the allowed root upwards to the
  volume root, as well as down through all source/target intermediate parent
  directories. This is to prevent relocation of a configured allowed-root
  subtree while the native move executes. If opening or validating any guard
  fails, the operation is refused; unusual volume layouts remain unsupported.
- New Windows tests cover same-size content mutation with a restored write
  timestamp, rejected concurrent writers, oversized-source rejection, and
  attempted relocation of a parent **above** the allowed root. Treat success
  as limited to the tested Windows CI runner and keep the code test-only.

### Still missing before any Agent integration

- Trusted approval transport between Node Agent and .NET Manager, with exact
  operation ID, command/device IDs, user confirmation decision, request digest,
  one-use nonces, deadlines, bounded payload size, and error-only/fail-closed
  handling. The current record snapshot cannot be accepted as an untrusted
  network-provided assertion.
- Separate portability/behavior tests on the actual target Windows build and
  supported volumes, including FAT/exFAT/NTFS/ReFS distinctions, network/UNC,
  mount/reparse behavior, reentrant opener interference, memory mappings and
  hardlinks. Fail closed on unsupported cases.
- Explicitly define how to handle allowed roots that are symlinks, Windows
  volume mount points or descendants of junctions. This research prototype
  requires plain ancestors and may reject otherwise legitimate paths.
- Directory moves remain unsupported. The registered Agent `move_path` tool
  remains disabled, and PR #26 remains Draft until Issue #27 is resolved.


## Local approval ticket research prototype (2026-10-08)

The .NET Manager now includes an **isolated, test-only**
`LocalMoveApprovalTicketPrototype`. It is NOT exposed to Node, the Manager UI,
Supabase, or any named pipe. It simulates the cryptographic portion of a future
Manager-issued grant after a human approves a specific move locally.

Properties exercised by its regression tests:

- HMAC-SHA-256 over the complete serialized payload using a local 32-byte key;
  verify MAC in constant time before parsing or trusting any operation fields.
- Versioned, bounded payload (8 KiB maximum) binding exact command ID,
  device ID, operation ID, source/destination/allowed-root strings, approved
  source SHA-256, fresh random nonce, issue time, and expiration.
- Ticket has a maximum two-minute lifetime; not-yet-valid and expired tickets
  are denied. A different HMAC key or any tampering is denied.
- An in-process one-use operation-ID cache rejects replay, including issuance
  of a new ticket with a different nonce for an already consumed operation.
  The cache fails closed at capacity instead of evicting valid replay entries.
- Disposal zeroes the test secret. These details demonstrate only a narrow
  cryptographic contract, **not an authenticated real transport**.

### Requirements before wiring to the normal Agent

1. Manager must issue a grant only **after an explicit local human approval**,
   using trusted Manager-captured filesystem identities and paths. A remote
   queued command must never be able to request that Manager sign a ticket
   merely by supplying self-declared `approved: true`.
2. Enforce one trusted caller and the lowest practical Windows named-pipe ACL;
   separate untrusted queue payloads from local approval state. The service
   must not accept arbitrary commands, shell strings, or chosen filesystem
   paths outside its own checked allowed-root policy.
3. Define and test a single **canonical cross-language wire representation**
   for Node and .NET, including schema version negotiation and downgrade
   refusal. The proof-of-concept JSON uses .NET serialization and is not an
   agreed, interoperable canonical encoding for external callers.
4. Key lifecycle: Manager-only protected key material (not embedded in repo or
   environment logs), safe rotation, secure storage, isolation per Windows
   user/device, and zeroization. Never send the HMAC key to Node or Supabase.
5. One-use operation IDs and nonces must be stored in the durable operation
   journal; the current memory-only cache **forgets replays after restart**.
   Atomic consume + execution-outcome journaling and uncertain-outcome
   recovery need explicit crash/timeout tests.
6. Verify source/root identities and content hash again at execution through
   the native file handles; HMAC authentication alone is not authorization.
   Resume and retries must be refused unless a fresh local approval occurs
   for a new operation ID.
7. Keep `move_path` disabled by default until the complete authenticated
   approval workflow, native file semantics, and adversarial Windows CI checks
   pass on the same final commit SHA. PR #26 stays Draft.


## Crash-persistent approval replay reservations and authenticated local IPC (2026-10-08)

### Persistent one-use grants (still research-only)

`DurableMoveApprovalReplayStorePrototype` reserves the SHA-256 of an operation
ID as a distinct `.used` marker under an explicit Manager-controlled
directory, using Windows atomic create-new semantics. The test-only
`LocalMoveApprovalTicketPrototype` can optionally be configured with this
store; on consumption it reserves the ID **before** returning success, and it
never deletes markers or falls back to the in-memory cache when disk storage
fails. Crash simulation, independent concurrent claimants, store tampering and
recreation of the Manager with an empty in-memory cache are covered by .NET
regression tests.

This provides a conservative no-replay rule under the tested OS/filesystem
semantics. It is **not** a transaction shared with a native file move or the
existing Node `OperationJournal`. A reserved but unexecuted operation must
remain `UNKNOWN_OUTCOME` / non-retriable until manually reconciled. Power-loss
durability of the directory entry, trusted directory ownership/ACLs, volume
reparse races and the 10,000-marker fail-closed limit still require review.
No cleanup should erase replay markers without a separately reviewed retention
policy. The current research store is not wired to actual Manager startup.

### Existing Manager ↔ Node Agent approval IPC is now authenticated

The existing Manager GUI already presents local approve/deny buttons for
registered confirmation-required tools. Previously its local named-pipe
`respond_approval` method accepted a request with only an operation ID and
decision. A different local client could call it without authenticating as
the Manager process.

In the feature branch, Manager now generates a **32-byte random session secret
on every Agent process launch**, passes it only to that child in
`PC_AGENT_LOCAL_APPROVAL_SECRET`, and stores it only in Manager process memory
for its lifetime. Both the Node Agent host config and privileged named-pipe
handler require a valid 64-character hex key; the Node side uses a constant-time
comparison. The Manager client attaches the key only for the privileged methods:

- `get_pending_approval` (privacy of pending file paths);
- `respond_approval` (approval integrity);
- `prepare_shutdown` (stop integrity).

Missing/malformed/wrong secrets are rejected without executing callbacks.
The host fails to launch if the secret is missing; Manager rotates the key
whenever it restarts the child. Read-only `get_health` and `get_version`
remain available without the secret. This is **hardening of the existing
confirmation path**, not permission to enable `move_path`.

### Remaining boundary and launch-policy concerns

- This is a **per-process bearer secret** carried through an inherited child
  environment variable. It is not a complete Windows process isolation
  boundary against programs with the same user's debugging/process-memory
  privileges. Verify named-pipe ACLs and same-user threat models.
- The Manager GUI's approval decision does not yet issue the signed
  `LocalMoveApprovalTicketPrototype` ticket; the ticket remains test-only
  and is not an accepted IPC method. There is deliberately **no new move
  execution RPC**. Durable replay is not integrated with native move/journal.
- Verify supported configuration upgrade behavior: manual Agent launches now
  require the separate per-launch key and must not fall back to the device
  token. Keep secrets out of diagnostics/log output and untrusted tools.
- `move_path` remains unregistered, with negative Node regression coverage;
  PR #26 must remain Draft until the production authorization transport and
  native file handling receive explicit security review and final Windows CI.


## 2026-10-08 — isolated approval-to-native-move integration (research)

Added `LocalApprovedNativeMoveWorkflowPrototype` in the Manager test assembly's
referenced application source. This **internal class is not reachable** from
the Manager UI, Agent, queue, or named-pipe IPC and must stay unreachable
until the production security gates are closed.

The prototype exercises the intended sequence:

1. Capture opened local file/parent/root identities, exact source SHA-256,
   destination and an operation ID as an immutable local proposal.
2. Simulate a **trusted local UI confirmation** (no ticket on denial). This
   deliberate test-only switch is **not a permission scheme** and must never
   be exposed as a request field to a queue or a network client.
3. Issue a short-lived HMAC ticket bound to exact command/device/operation/
   source/destination/root/hash values.
4. Verify ticket integrity and freshness; atomically reserve the operation ID
   using the separate crash-persistent replay store *before* the native call.
5. Invoke Windows handle-relative no-clobber rename with approved object
   identity, path-chain guards and content hash validation. No automatic
   retry/rollback after a failed or uncertain outcome.

Manager Windows CI now tests successful local proposal→confirmation→move,
denied confirmation, tampered HMAC, stale ticket, changed source, existing
target refusal followed by a blocked restart-time retry, and simulated
termination **after durable reservation but before native rename**. The latter
test intentionally sacrifices availability in favor of fail-closed behavior.

### Live local approval channel: per-dialog challenge

In addition to the per-Agent-launch secret, each pending approval request
now carries a fresh 128-bit random `approval_nonce`. The real Manager dialog
echoes it with the operation ID and the user's decision, and Node rejects
missing, stale, and mismatched values. Distinct pending instances with the same
operation ID are no longer treated as the same GUI dialog. The privileged
named-pipe methods still require the process credential; a challenge
**does not replace** authentication.

### Production status and incomplete work

- `move_path` remains disabled in the normal Agent tool registry.
- There is **no** production-issued signed move grant, IPC method for native
  move, automatic approval, or file mutation callback from the queue. The
  existing Manager yes/no dialog applies only to already-registered tools.
- The local replay store is not yet the Manager's trusted, ACL-protected
  operational journal. Crash resilience across actual storage power loss,
  concurrent process ownership and log integrity need independent validation.
- The native `ntdll` prototype is not certified on different Windows builds,
  SMB/UNC, alternate filesystems, mapped-file writers, hardlinks or reparse/
  mount-point environments.
- Windows named pipe creation ACLs, same-user adversaries and inspection of
  another process's launch environment remain open research items.
- Merging PR #26 or enabling `move_path` would currently be premature.


## Local named-pipe lifetime, framing and ACL research (2026-10-08)

The existing Manager ↔ Node Agent local IPC now has additional defense in depth:

- The Manager creates a fresh 128-bit random suffix for its named pipe **per
  Manager instance**, instead of only a predictable Windows user SID. This
  reduces pre-binding / pipe-name-squatting risk, but does not authenticate a
  client or provide strong OS security by itself.
- Node's `server.listen({ path, readableAll: false, writableAll: false,
  exclusive: true })` explicitly opts out of the Node APIs that broaden pipe
  read/write access to all Windows users. It also limits active sockets to
  32, drops idle connections after five seconds, and executes at most one
  newline-delimited request per connection.
- The real Manager client now **requires the exact GUID request ID in every
  reply**; responses with forged/missing IDs are rejected even if their
  `ok` field claims success. Replies are capped at 16,384 decoded characters
  before JSON parsing, and local IPC already has a two-second request timeout.
- Windows CI regression tests cover two pipelined privileged commands (only
  the first callback runs), idle-client timeout, distinct Manager pipe names,
  spoofed response IDs and oversized responses.
- The existing per-Agent-launch random secret and per-dialog approval nonce
  remain required for privileged approval/status details and shutdown methods.

### OS ACL limitation: not a completed security gate

**Node's `readableAll:false` and `writableAll:false` are not a custom,
audited Windows pipe DACL.** The Windows default named-pipe security
descriptor can grant read permissions to Everyone and Anonymous, as described
in [Microsoft Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).
The current Node `net` API does not expose a `CreateNamedPipeW`
`SECURITY_ATTRIBUTES` security descriptor parameter at server creation.
Therefore an explicit **owner-only or logon-session-scoped DACL has not yet
been installed or validated**.

Before exposing a native file mutation IPC method, choose and test one of:
(1) a trusted Windows-native/.NET pipe server with an explicit, locked-down
DACL and verified caller identity, and a separately authenticated Node
request channel; or (2) a carefully audited native pipe-binding helper that
supports exact DACLs at creation and first-instance ownership. Tests must
attempt cross-user/logon-session access, pre-binding/squatting, restart
races, ACL inspection and simulated same-user process compromise.
Any unsupported environment must refuse file mutation and never fall back
to a world-readable/writable IPC endpoint.

**Production status remains unchanged:** `move_path` is unregistered;
`LocalApprovedNativeMoveWorkflowPrototype` is internal and not reachable
through the ordinary Agent/Manager UI. No `main` merge or deployment.


## 2026-10-08: kernel-verified owner-only pipe ACL research

A separate, **test-only** .NET 8 implementation now lives in
`manager/PcAgentManager/Services/OwnerOnlyNamedPipePrototype.cs`. It does
NOT replace the existing Node Agent `net.createServer()` and contains no
remote move/approval request handler.

This uses .NET 8's built-in `NamedPipeServerStreamAcl.Create` and passes an
explicit Windows `PipeSecurity` descriptor **at initial server creation**:

- The Windows process user SID is the sole explicit `Allow` principal.
- The DACL is protected against inheritance, its owner is that user SID,
  and the pipe handle is not inheritable by child processes.
- The factory rejects arbitrary pipe names; only disposable test-only names
  containing a 128-bit hex nonce are accepted.
- After OS pipe creation, the code obtains the **actual handle DACL** using
  `GetAccessControl()`, checks the owner, protected/non-inherited ACL, the
  single owner allow ACE, and required read/write access. Unexpected ACLs
  cause fail-closed disposal before any request is handled.
- No override uses `PipeOptions.CurrentUserOnly`, because .NET explicitly
  documents that mode as **ignoring the caller-provided PipeSecurity**.

The Windows Manager CI run for functional SHA `dc88072` passed three
security-specific regression tests:

1. Reads back the actual native ACL and confirms no broad Everyone,
   Anonymous or BuiltinUsers grant.
2. Opens the pipe as the real current Windows user and exchanges PING/PONG;
   invalid/malicious pipe names are refused.
3. Creates a competing same-name server instance first, then confirms the
   secure factory fails instead of using the attacker-owned endpoint.

The original attempt added the nonexistent
`System.IO.Pipes.AccessControl 8.0.0` NuGet package, which failed at
restore with `NU1102`. This was corrected by using .NET 8's standard
Windows framework APIs without the nonexistent package. Both Agent and
Manager CI passed at `dc88072`, including the Manager Windows package.

### This is progress, not production completion

- **No OS-level different-Windows-user connection attempt was executed**.
  Structural readback of an explicit owner-only ACL is strong evidence of the
  configured security descriptor, but cannot replace a genuine cross-account
  unauthorized-client probe or a same-user attacker threat model.
- The normal Agent approval named pipe is still created by Node. The new
  .NET ACL server is only a research fixture. **The existing Node pipe is not
  owner-only on the strength of these tests.**
- The eventual native move IPC should be **Manager-owned and server-first**
  with explicit owner/logon-scoped DACL, verified caller identity, named-pipe
  first-instance/anti-squatting semantics, bounded versioned message framing,
  trusted local confirmation, durable operation-journal reservation and
  request-specific authentication. Do not allow the remote queue or local
  Node client to mint its own trusted approval.
- Investigate whether multiple user sessions or service accounts need access,
  without broadening to Everyone, Anonymous or BuiltinUsers. Explicitly test
  different Windows user accounts on an isolated test machine.
- Do not bolt a post-creation DACL change onto the old Node listener: the
  interval between creating it and locking down its ACL is an unnecessary
  race. Create the correct protected pipe **atomically from the start**.
- This new fixture does not make experimental `move_path` accessible.
  Keep PR #26 Draft and Issue #27 open.

References:
- [Microsoft named-pipe security and access rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).
- [.NET NamedPipeServerStreamAcl.Create](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeserverstreamacl.create?view=net-8.0).


## Actual cross-user Windows pipe-denial gate (2026-10-08)

The previous owner-only DACL experiment now has an **actual Windows
cross-account connection test**, not just a descriptor inspection.

- GitHub-hosted Windows CI creates a temporary, unprivileged local user with
  a randomly generated password. It does **not** use any existing user
  account or transmit credentials to logs, connected apps or the Agent.
  It removes the user in a `finally` block after the Manager regression.
- The test uses Windows `LogonUserW` to get that temporary user's genuine
  Windows logon token and `WindowsIdentity.RunImpersonated` to execute
  `CreateFileW` against the live named-pipe server as the alternate
  principal, with read/write access requested.
- **Success requires `CreateFileW` to fail with Windows error 5
  (`ERROR_ACCESS_DENIED`)**. Timeouts, missing pipe, invalid credentials,
  account SID equal to the owner, or other Win32 failures fail the test.
- The server's actual ACL is read back and verified after the negative
  connection attempt; the original authorized owner must still be able to
  connect successfully.
- The Manager CI job now sets `PC_AGENT_REQUIRE_ALT_USER_TEST=1`, making
  absence of the temporary account a test failure rather than a silent skip.
  Development machines without this test fixture print a clear SKIP marker
  for the standalone cross-account case.
- **Windows CI at SHA `73320e6` passed**: actual cross-user
  `ERROR_ACCESS_DENIED` test, Manager regression, portable Windows app
  packaging, and Agent's 108 Node tests (zero failures).

This demonstrates cross-account isolation of the **test-only .NET ACL pipe**
on the hosted Windows runner. It does **not** prove security against
malicious code running as the **same Windows user** with debugger/process
memory access, nor that Node's currently active IPC pipe uses this ACL.
It is not a separate-process adversarial test with elevation and service
accounts. Continue to protect the Manager's per-launch authorization secret
and bind all pending confirmations to their one-use dialog nonces.

### Next native integration gate

A real Manager-owned secured pipe listener and a narrowly scoped,
versioned request protocol must be constructed **without exposing move
execution to the remote Agent** until the complete trusted UI approval,
durable replay journal, root containment, file identity and crash
semantics are validated. Ensure the listener uses the audited ACL
**on the first server-instance creation**. Never modify the insecure Node
pipe ACL after it is already accepting connections, and never claim
`move_path` is production-ready based solely on this experiment.

`move_path` remains unregistered; PR #26 remains Draft; Issue #27 remains open.


## Manager-owned protected status endpoint (2026-10-08, read-only)

The earlier .NET ACL proof-of-concept is now reused in a separate Manager
component, `ManagerProtectedPipeHost`. This is a **minimal local status
boundary**, not a native file-move channel.

### What is implemented

- `OwnerOnlyNamedPipePrototype.CreateManagerStatusPipe` uses the same
  DACL-verified `NamedPipeServerStreamAcl.Create` factory previously
  validated by cross-user Windows CI. The Manager-specific prefix requires a
  fresh 128-bit random hex suffix.
- A single secured native Windows pipe handle remains open for the whole host
  lifetime. Individual connections are accepted using this same object;
  the server is not deleted/re-created between clients, avoiding a
  re-binding/name-squatting gap.
- Protocol **only**: exact ASCII `PING 1\n` yields `PONG 1\n`. Every
  other request, including `approve` or `move_path`, yields `DENIED\n`.
  There is **no generic JSON dispatcher, shell, file access, external
  application tool, grant signer or authentication callback**.
- Request parsing has a maximum of 32 ASCII bytes, rejects control/non-ASCII
  characters and processes one request per connection. Each connection has a
  2-second read/write timeout. Host disposal cancels outstanding accepts,
  closes the handle and stops the listener.
- The ordinary Windows Manager GUI now starts this **optional read-only**
  boundary and disposes it when the GUI closes. If ACL verification or pipe
  creation fails, the Manager logs its disabled status (without the pipe name
  or any secret); the existing Agent workflow remains unchanged. There is
  **no fallback** that exposes this feature via a less-secure pipe.
- Neither the Agent nor the cloud relay receives a protected-pipe endpoint
  name, nor can either invoke a new native action.

### Windows CI evidence and limits

Manager regression exercises multiple successive PING connections, denial
of wrong protocol versions/approval/move commands and oversized data, fresh
random names, server shutdown, and actual Windows `CreateFileW` denial
under an impersonated **different local user**. The cross-user test
is mandatory in CI, using a temporary Windows account removed after tests.

The CI can establish successful operation in the tested Windows runner, not
guarantee it will function on every user's device. The new secured endpoint
is **strictly read-only**; it is not a substitute for the existing Agent
named pipe (which still uses Node), not an authorization broker, and
**not yet a production-ready native move protocol**.

### Further gates before allowing native file mutation

1. Design a strict, fixed, schema-validated Manager **request** protocol with
   OS-level caller verification and explicit binding to the Manager's *real*
   local UI approval decision; never take `approved: true` from the Agent.
2. Maintain durable, atomic operation-ID reservation and outcome journaling,
   including crash/power-loss recovery and unknown-outcome reporting.
3. Preserve source content/identity, allowed-root containment, no-replace
   rename and all supported Windows filesystem/reparse semantics.
4. Test same-user malicious process behavior, administrator/service account
   boundaries, pipe name discovery and unsupported OS configurations.
5. Confirm final same-commit CI plus physical Windows device validation.

Until those are reviewed and implemented, `move_path` stays unregistered,
PR #26 stays Draft and Issue #27 remains open.


## 2026-10-08: owner-only replay-marker directory experiment

The native no-replace file-move prototype already has a test-only durable
`.used` replay reservation store, which prevents reuse of an operation ID
after a restart. The remaining filesystem-permission weakness was that the
test store accepted a caller-selected directory created using the ordinary
parent ACL.

**New isolated, Windows-only directory experiment:**

- `OwnerOnlyReplayDirectoryPrototype.CreateNewTestDirectory` uses native
  `CreateDirectoryW` **with a protected, non-inherited security descriptor
  supplied during directory creation**, rather than creating an insecure
  directory and applying a DACL afterward. The sole allow ACE grants the
  current Windows user SID full access; child files and directories inherit
  that principal-only grant. The API only accepts randomly named test
  directories below a separately trusted, existing, non-reparse parent.
- Directory creation is **create-new only**: a pre-existing directory is an
  error, never silently adopted, overwritten or ACL-reset. After creation,
  the code reads back the actual Windows owner and DACL from disk and refuses
  a missing owner, inherited rules, broad grants, reparse points or an
  unexpected ACE.
- `DurableMoveApprovalReplayStorePrototype` now exposes an **opt-in,
  test-only strict mode** (`requireOwnerOnlyDirectoryForTest`). This mode
  refuses to create the directory implicitly: it demands the native
  protected directory and verifies its DACL again before every atomic
  `CreateNew` approval reservation. No fallback to an unprotected
  directory is permitted in this mode.
- Manager regression tests cover protected directory creation, the actual
  marker file's inherited ACL, atomic reservation, denied replay after
  reopening the store, refusal to adopt a preexisting directory, refusal of
  malformed paths, and rejection of an absent directory in strict mode.
- The Windows GitHub CI runner's temporary unprivileged second account makes
  a **real impersonated `CreateFileW(CREATE_NEW)` call** for a marker under
  this protected directory. The test passes **only with
  `ERROR_ACCESS_DENIED (5)`** and confirms no marker appeared. Missing
  alternate credentials fail CI, not silently skip. Home-PC regression tests
  deliberately skip this alternate-user case rather than creating accounts.

### Still unproven and not enabled

**These are safety tests, not a production move mechanism.**
The new directory helper accepts a *trusted-parent* assumption and checks
only the immediate parent against reparse links; it does **not** hold all
ancestor directory handles or eliminate a same-user or privileged attacker
racing path replacement between DACL checks and marker creation. The
existing durable store still cannot prove directory-entry persistence after
an abrupt power loss, retained journal integrity for every filesystem,
or an atomic durable file-move outcome record. Other Manager methods that
instantiate the legacy test store without strict mode remain intentionally
unchanged. The normal Manager has no active replay reservation endpoint.

Before enabling actual native file mutation: pin root/parent identity and
ACL with native held handles, establish tested power-loss durability,
validate file identity, native no-clobber rename and same-user threat model,
and bind authorization to the **real Manager-local UI decision**.

Do **not** register `move_path`, merge PR #26 or close Issue #27 based on
this experiment.


## 2026-10-08: staged Manager-native move confirmation (still not production)

The existing Windows Manager UI already has an authenticated Node Agent
approval reply with an operation-specific `approval_nonce`. The experimental
native move workflow was separate and originally used
`ConfirmForTest(proposal, simulatedLocalUserApproved: true)`. The following
research narrows that gap **without enabling native move IPC**.

### What now exists

- `LocalMoveDialogConsentPrototype` creates a new cryptographically random,
  **128-bit per-dialog nonce**, and a read-only display snapshot of the exact
  captured command ID, device ID, operation ID, canonical source/destination,
  approved root and source SHA-256. One instance can have only one pending
  dialog; pending requests cannot silently replace one another.
- A confirmation is accepted at most **once** and only against the exact
  **in-process dialog object**, and within a maximum **30-second** issued-at
  and expires-at window. A stale/expired/copied/changed challenge, overlapping
  dialog, cancelled/closed dialog, and every result other than an explicit
  `DialogResult.Yes` fail closed. The pending challenge is consumed before
  ticket issuance, even if the signer subsequently refuses it.
- `LocalMoveConfirmationFormPrototype` is a native dark-themed Windows
  Forms modal prototype displaying the **exact trusted request fields**,
  including file hash and deadline. Approve is initially disabled until the
  local person acknowledges the displayed paths/operation. Escape or
  closing defaults to denial; Enter alone cannot approve.
- `PromptOnManagerUiThreadForTest` is an **STA-only local WinForms research
  bridge** that shows this modal, then passes its result through the
  one-use confirmation gate. It clears pending state even if WinForms throws.
- The previous `LocalApprovedNativeMoveWorkflowPrototype` and HMAC ticket
  flow are used for the test-only positive path, including validation of the
  captured filesystem snapshot, a strict owner-only durable replay marker
  reservation, and native no-replace rename. Neither the Agent registry nor
  the Manager's normal `MainForm` invokes this path.
- Windows regressions verify that a matching test-local dialog decision
  can produce **one** ticket and **one** no-clobber move, while a second
  execution is denied by the replay store. Separate tests cover copied dialog
  data, reused operation ID with stale nonce, denied/cancelled/implicit OK,
  expired and time-reversed replies, overlapping prompts, no mutation from
  preview alone, and form rendering/buttons on a Windows STA thread.

### Important trust boundary and remaining work

**This is not proof of a real human clicking a production dialog.** The
regression harness feeds simulated WinForms `DialogResult` values to
`ResolveLocalDialogForTest`; the separate form inspection is
non-interactive. Neither automated case is evidence of a human approving
a production file move. The offline `PromptOnManagerUiThreadForTest`
WinForms bridge is implemented but is **not wired to an ordinary UI action**
or runtime command.

A `DialogResult.Yes` object supplied by arbitrary code is **not** an
authentication credential. Before production integration, remove the
test-only simulated-boolean issuer from reachable paths; create a
Manager-owned, local-UI-only capability and ensure native action requests
cannot call the issuer, inject a dialog result, or smuggle a signed
approval through Node/cloud IPC. A real manual GUI/Win32 desktop test on
the same signed release SHA must verify visible text, focus, checkbox,
time-limit behavior, consent and denial. Do not rely on code-reference
identity or dialog nonces alone against malicious programs running as
the same Windows user.

Native replay journal ancestors, same-user attacker/race assumptions,
filesystem support, directory-entry power-loss durability, and crash
outcome reconciliation remain unresolved. No `move_path` tool is registered;
no native move RPC is reachable; PR #26 stays Draft and Issue #27 remains open.
