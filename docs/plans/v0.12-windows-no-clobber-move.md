# v0.12 Windows no-clobber move: implementation design and release gate

Status: **design only / not approved for deployment**. Tracks [Issue #27](https://github.com/EliteMay/pc-agent/issues/27) and draft [PR #26](https://github.com/EliteMay/pc-agent/pull/26).

## Problem and temporary safety policy

Node `fs.renameSync(source, destination)` is called after a separate
`existsSync(destination)` check. Another process can create the destination in
between; the implementation cannot promise "never overwrite". The production
`registerSafeWriteTools` therefore **does not register `move_path`** until a
proper provider and adversarial tests pass. Keep that fail-closed default in
place; do not add a configuration flag that simply turns the unsafe rename
path back on.

The legacy `move-path.js` implementation and its direct-call regression tests
remain for development, not remote execution.

## Proposed Windows implementation

Use a small trusted Windows-native operation boundary that ships with the
Manager, not a shell command assembled from queued strings.

1. Expose one fixed operation: `move_no_replace(source_path, destination_path,
   approved_source_identity, allowed_roots)`. Inputs are data, not code or
   command-line fragments. Authenticate the local caller and bound request size.
2. In native/.NET interop, open a handle to the **source** using Windows
   `CreateFileW` with the permissions and sharing modes required for renaming.
   For a directory, handle opening requires `FILE_FLAG_BACKUP_SEMANTICS`.
   Reject symbolic links/reparse points and unsupported file types according
   to the policy. Compare the *opened object* identity (e.g. volume and file
   ID via `GetFileInformationByHandleEx(FileIdInfo)`) with the approved object.
   A path-only `stat` before a rename is insufficient.
3. Open the **destination parent** as a trusted directory handle. Check its
   resolved final path and the source final path against canonical allowed
   root identities using the same Windows path-normalization rules. Explicitly
   reject path components that redirect outside allowed roots. Decide how
   relocation of an allowed-root directory while handles remain open is
   prevented or detected; merely resolving a name once is insufficient.
4. Rename the *source handle* with
   `SetFileInformationByHandle(FileRenameInfo, FILE_RENAME_INFO)`, with
   `ReplaceIfExists = FALSE`. Supply the target file name **relative to the
   opened destination directory handle** using `RootDirectory` when supported.
   Do **not** set `FILE_RENAME_REPLACE_IF_EXISTS`, POSIX replacement semantics,
   `MOVEFILE_COPY_ALLOWED`, or any other replacement/fallback behavior.
   An existing destination must cause the operation to fail atomically, even
   when another process created it milliseconds earlier.
5. Keep source and destination-parent handles alive through the rename
   boundary. Verify post-operation result and report a structured failure
   without deleting or replacing any third-party destination.
6. Limit the first provider to regular files if that is necessary. Directory
   moves must remain disabled until directory content/reparse-point and
   descendant-scope semantics are defined and tested. File-system permissions,
   hardlinks, and directory descendants require an explicit threat-model
   review.
7. On helper absence, helper version mismatch, failed identity check,
   unsupported filesystem, or uncertain outcome: **fail closed**. Do not
   retry a possibly completed mutation automatically; keep the journal's
   `UNKNOWN_OUTCOME` semantics.

## Acceptance tests (must run on Windows)

- Normal file rename within one allowed volume succeeds and preserves bytes.
- Already existing file or directory destination is not replaced.
- **Deterministic race:** insert a test barrier immediately before the
  handle-based rename, create a different destination, then release the
  barrier. Assert `move_no_replace` fails, competing destination bytes and
  identity are unchanged, and source remains.
- Source object replaced with same-size/same-content file after approval:
  fail without moving substitute.
- Source object replaced after validation but before native handle opening:
  fail without moving substitute.
- Destination parent replaced by a junction to a directory outside allowed
  roots: fail without writing outside.
- Source parent replaced by a junction outside allowed roots: fail.
- No cross-volume move/copy fallback, including junction/reparse mount points.
- Root-move, move-into-own-descendant, sensitive file/dir, reserved names,
  alternate data streams: fail.
- Process crash/timeout after native operation: journal reports uncertain
  outcome and does not blindly retry or perform unsafe cleanup.
- Different Windows filesystem types and file permissions: explicitly
  document supported matrix; unsupported cases fail closed.
- Agent CI, Manager CI, and an independent physical Windows PC all green
  on the **same final commit SHA**.

## Re-enable criteria

Only re-register `move_path` when all acceptance tests pass and review
confirms that the native helper's guarantees match the public tool description.
The test `unsafe move_path stays unavailable in the runtime registry` must
then be replaced with tests proving the safe provider is the only
registration path; do not silently weaken it.

## Windows API documentation

- [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info): `ReplaceIfExists = FALSE`
  returns an error if the target name exists; `RootDirectory` can hold the
  directory for a relative target name.
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle):
  mutate an opened file object using a handle with the required access rights.
- [MS-FSCC FileRenameInformationEx](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c):
  replacement is explicitly gated by `FILE_RENAME_REPLACE_IF_EXISTS`.

**Design limitation:** these docs describe available Windows API semantics.
They do not by themselves prove the specific interop code is race-safe.
That proof requires the adversarial Windows tests and review above.


## Research update: isolated .NET prototype (2026-10-08)

An **unregistered, test-only** interop experiment now lives in
`manager/PcAgentManager/Services/WindowsNoReplaceMovePrototype.cs`.
Its tests are in `manager/PcAgentManager.Tests/Program.cs`.

- Initial experiment: Win32 `SetFileInformationByHandle(FileRenameInfo)`,
  relative target name, `RootDirectory` set to an already-open destination
  directory handle. GitHub Windows Manager CI **failed** the normal rename
  with Win32 `ERROR_INVALID_PARAMETER (87)`. Consequently, the two
  non-overwrite tests that expected *any failure* were not proof of correct
  no-clobber semantics.
- Follow-up experiment: `RootDirectory = NULL`, full destination path.
  This follows the commonly documented Win32 usage and is tested separately.
  **However, a full destination path can be re-resolved after validation,
  so destination-parent junction races remain unresolved.**
- Even if the three prototype tests pass, the helper cannot be wired into
  the normal Agent, because it currently does not enforce approval identity,
  allowed-root containment through the rename boundary, or all required
  adversarial source/parent substitution cases.
- This experiment deliberately does **not** re-register `move_path`.

References:
- [Microsoft FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info):
  `ReplaceIfExists=FALSE` means the operation fails when target exists.
- [RootDirectory / error 87 reports](https://learn.microsoft.com/ja-jp/answers/questions/6015074/setfileinformationbyhandle-filerenameinfo-rootdire):
  user-observed Win32 relative-handle behavior can differ from the documented
  usage. Investigate a supported, handle-anchored native alternative
  without downgrading allowed-root and anti-junction guarantees.

- **Agent CI:** passed (99 Node tests).
- **Manager regression tests:** passed, including the three isolated Windows

## Approval identity and reparse-race research prototype (2026-10-08)

The Manager now has **test-only** `CaptureApprovalForTest` and a guarded
`MoveFileForTest(..., approved, operationId)` code path. No normal Agent or
Manager UI uses these methods.

The capture stores an immutable in-memory snapshot of:

- the approval operation ID and exact source/destination/allowed-root paths;
- Windows object IDs (volume serial + file indices) for source, destination
  parent, and allowed root, from `GetFileInformationByHandle`;
- source length and last-write metadata, plus normalized final paths observed
  via `GetFinalPathNameByHandleW`.

The test-only executor compares those values against opened handles and a
fresh lookup of each pathname, both **before** and **after** an injected
precommit test callback. It rejects mismatched operation IDs, swapped source
files with identical bytes, different destination-parent directory objects,
and moved parent handles. Capture and revalidation refuse source/destination
paths outside the canonical allowed root and reparse entries at directly
opened filesystem objects.

Windows regression scenarios added:

- unchanged approved file can be moved within the allowed root;
- approved source replaced by a new file with the same bytes: denied;
- destination parent replaced after approval: denied;
- destination parent replaced after handles were opened, at a deterministic
  precommit barrier: denied;
- source outside the allowed root: denied;
- **junction redirect** of the destination parent to an outside, disposable
  test fixture at the precommit barrier: denied, no file appears outside;
- approval for operation A cannot be reused as operation B.

### Security limits (release blockers still open)

1. **Not atomic with path resolution.** The native
   `SetFileInformationByHandle(FileRenameInfo)` call currently uses a full
   destination pathname because `RootDirectory` did not work in the tested
   Win32 code path. The destination parent can still change in the tiny
   interval between the final validation and this kernel operation. These
   deterministic tests narrow the observable window but **cannot prove that
   an arbitrary attacker cannot exploit it**.
2. **No end-to-end approval transport.** The snapshot is an in-memory
   .NET test object, not a signed remote payload nor a hooked-up Agent
   approval result. `operationId` binding demonstrates the intended contract
   but is not yet an authenticated cross-process protocol.
3. **Only regular files are eligible.** Directory moves, recursive sensitive
   child checks, mount/reparse complexities, SMB/network filesystems, and
   hardlink threat modeling are not complete.
4. **Parent/root relocation races remain.** The opened handles are kept
   alive, but the absolute destination path is still re-resolved by Windows.
   Implement and prove a handle-anchored, atomic no-replace operation before
   exposing the helper to any normal Agent caller.
5. **Deployment disabled.** `move_path` stays unregistered in
   `registerSafeWriteTools`. Do not weaken or bypass the negative registry
   test. See security release gate [Issue #27](https://github.com/EliteMay/pc-agent/issues/27).

The junction test uses `cmd /c mklink /J` **only to create a disposable test
fixture in Windows CI**, not as any application command execution feature.


## NT handle-relative rename research (2026-10-08)

An additional **test-only** implementation is now isolated in
`manager/PcAgentManager/Services/WindowsNtAnchoredMovePrototype.cs`. It is
called from `WindowsNoReplaceMovePrototype.MoveFileForTest` only when the
explicit `useNativeRelativeMoveForTest: true` argument is supplied together
with the local approval snapshot and matching operation ID. **The normal
Agent registry still does not expose `move_path`.**

### Mechanism and observed Windows CI results

- Uses the native `ntdll!NtSetInformationFile` interface with
  `FileRenameInformation` and a `FILE_RENAME_INFORMATION` buffer that sets
  `ReplaceIfExists = FALSE`, `RootDirectory` to an already-open destination
  parent **handle**, and `FileName` to one validated relative leaf.
- The Windows API is asked to do a single no-replace rename of the opened
  source handle relative to that directory object. It is not passed a mutable
  absolute destination pathname at this final operation.
- Native NTSTATUS failures are converted with `RtlNtStatusToDosError` and
  treated as failure. A pending/uncertain outcome is never automatically
  retried; no cleanup blindly removes a possible competing destination.
- In addition to approved object identity/final-path revalidation, source and
  destination parent directory chains from the allowed root are opened with
  sharing that excludes `FILE_SHARE_DELETE`, and are kept alive until the
  final native operation. This is intended to prevent intermediate parent
  relocation in ordinary Windows filesystem scenarios.
- Functional commit `3cdfbb1` passed **Agent CI and Manager CI**, including
  successful native move, preexisting destination, last-moment competing
  destination, direct parent relocation prevention, and equal-byte source
  replacement refusal. Follow-up directory-chain guard tests run separately.

### Important limitations and remaining release blockers

1. `NtSetInformationFile` is documented in the Windows driver/NT-native API
   documentation. Shipping it through user-mode `ntdll.dll` raises
   compatibility and support questions; working GitHub Actions tests do not
   establish support on all target Windows builds/filesystems.
2. The current chain lock begins at the configured root. An ancestor **above**
   that root could be renamed, and supported semantics for rename/mount-point
   races across ancestor objects still need analysis and adversarial tests.
3. The snapshot captures source file ID, size, and last-write metadata, but
   does not bind the full file content to a cryptographic hash nor lock all
   writers. Approval scope and source modifications through other handles or
   hardlinks need further threat-model review.
4. Destination names are checked for ordinary Windows-invalid patterns,
   but edge cases (8.3 aliases, case sensitivity, hardlinks, mount points,
   unusual filesystems, and network targets) require additional validation.
5. This is an **internal test-only experiment** with no authenticated
   cross-process helper protocol and no Agent integration. Do not use the
   regression tests as grounds to re-enable `move_path` or merge PR #26.

Reference: [Microsoft NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile)
for native `FileRenameInformation`; see [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)
for no-overwrite intent.


## Content integrity and volume-ancestor guard research (2026-10-08)

An additional **test-only** guard is implemented in the .NET move prototype:

- Capture SHA-256 of at most 64 MiB from the **opened source handle**, as part
  of its locally approved immutable snapshot. Recompute that digest through
  the opened handle before each native rename. This rejects modifications to
  the original file even if its length and last-write timestamp are restored.
- While the NT-relative move is executing, its source file is opened without
  `FILE_SHARE_WRITE` or `FILE_SHARE_DELETE`. Concurrent open-for-write
  requests ordinarily fail with a sharing error. Test-only callbacks exercise
  this behavior at the last precommit boundary. This is **not** a claim that
  memory-mapped writes, filesystem-specific behavior, or all hardlink races
  have been eliminated.
- Extend open-handle no-delete guards from the allowed root upwards to the
  volume root, as well as down through all source/target intermediate parent
  directories. This is to prevent relocation of a configured allowed-root
  subtree while the native move executes. If opening or validating any guard
  fails, the operation is refused; unusual volume layouts remain unsupported.
- New Windows tests cover same-size content mutation with a restored write
  timestamp, rejected concurrent writers, oversized-source rejection, and
  attempted relocation of a parent **above** the allowed root. Treat success
  as limited to the tested Windows CI runner and keep the code test-only.

### Still missing before any Agent integration

- Trusted approval transport between Node Agent and .NET Manager, with exact
  operation ID, command/device IDs, user confirmation decision, request digest,
  one-use nonces, deadlines, bounded payload size, and error-only/fail-closed
  handling. The current record snapshot cannot be accepted as an untrusted
  network-provided assertion.
- Separate portability/behavior tests on the actual target Windows build and
  supported volumes, including FAT/exFAT/NTFS/ReFS distinctions, network/UNC,
  mount/reparse behavior, reentrant opener interference, memory mappings and
  hardlinks. Fail closed on unsupported cases.
- Explicitly define how to handle allowed roots that are symlinks, Windows
  volume mount points or descendants of junctions. This research prototype
  requires plain ancestors and may reject otherwise legitimate paths.
- Directory moves remain unsupported. The registered Agent `move_path` tool
  remains disabled, and PR #26 remains Draft until Issue #27 is resolved.
